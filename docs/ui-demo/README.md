# HomeProxy 界面重构 — 四个设计稿

打开方式：直接双击 HTML 文件（纯静态，无依赖）。

| | 文件 | 布局哲学 | 状态 |
|---|---|---|---|
| **A** | `demo-a-dashboard.html` | **驾驶舱式**：左侧分组导航 + 顶部全局条 + 卡片网格总览 | 备选 |
| **B** | `demo-b-wizard.html` | **向导式**：窄工具轨 + 中央三步流程 + 右侧常驻状态栏 | 备选 |
| **C** | `demo-c-policy-grouped.html` | A 的视觉 + 路由/DNS/规则 归入「流量策略」（**换成侧栏导航**） | 备选 |
| **D** | `demo-d-existing-ia.html` | **保留现有两级 tab 模式**，只调层级：访问控制升到一级，客户端设置新增「节点配置」并收敛为五项 | **当前方向** |

四稿都可以点：侧栏可切页、状态按钮可切三态；B 的步骤条/节点选择/工具轨可点；C 多两个可点的东西（规则页类型筛选、策略卡跳转）；D 的两级 tab 全可点（客户端设置下 5 个二级 tab），另含「改动摘要」「迁移对照」两页。

> **C 与 D 的关系**：两者的目标信息架构是同一套（分流 / DNS / 规则集 归为一组，访问控制独立出来），
> 区别只在**导航范式**——C 换成侧栏，D 保留现有两级 tab。D 更贴近"在现有 UI 上改版扩充"。

---

## A / B 两稿共同基于的现有优势（不是凭空画的）

这一轮重构之后，有几件事**第一次变得可以放心做**：

| 现有能力 | A / B 两稿里用到的地方 |
|---|---|
| 协议是**一张有序表**（17 项，含 `sides` 与 `feature`） | A 的"按协议批量操作"、B 的入站/节点协议徽章，两侧列表天然一致 |
| `singbox_get_features` 驱动门槛 | 带 QUIC 徽章的协议**说明为什么不可用**，而不是直接消失 |
| `node_parse` RPC | 「粘贴分享链接」当成一等入口，并承诺指出**哪一段**不合法 |
| 状态**三态**（RUNNING / NOT RUNNING / STATUS UNKNOWN） | A 的顶部状态药丸 + hero 卡、B 的右侧状态块；两稿都能切给你看 |
| `acllist_*` / `resources_*` / `connection_check` / `certificate_write` / `log_clean` | 各自有明确界面位，不是占位符 |
| 更新是**事务性**的（有锁、有回滚） | B 的订阅页把"中途失败整份回滚"写进提示 |

数据也是真的：节点用的是你真机导入的那 4 个（anytls / hysteria2 / shadowsocks / vless），
分流清单、DNS、端口都取自出厂配置。

## A 与 B 怎么选：六个维度

| 维度 | A 驾驶舱式 | B 向导式 |
|---|---|---|
| **首屏回答什么** | "现在通不通、走哪个节点、分流怎么走" —— **三问一屏** | "我下一步该干什么" —— **一次一件事** |
| **导航** | 功能分区（概览/节点/分流/DNS/服务端/系统） | 任务流程（步骤 1-2-3）+ 工具轨 |
| **新手** | 需要自己找入口；空状态较朴素 | 空状态会**教学**，步骤完成会打勾 |
| **高频运维** | 改一项 = 进对应页 → 改 → 保存；**步数少** | 步骤流对"改一项"略绕，但状态栏常驻、不用来回切页 |
| **信息密度** | 高（一屏能看到很多） | 中（留白多，视线集中） |
| **出问题时** | 状态在顶部，一眼可见 | 状态**永远在右侧**，切到任何页都不丢 |

### 在 LuCI 里的实现成本（这是最实际的约束）

- **A：中。** 它的结构与 CBI 天然吻合——`form.Map` + 分区 + `GridSection` 表格 + 卡片式 CSS。
  现有代码已经在用这套（`NamedSection`/`GridSection`/`Value`），**大部分是重排 + 样式**，
  少量自定义（hero 卡、协议徽章）。
- **B：高。** 步骤流、常驻状态栏、"选中即生效"都不是 CBI 的惯用法，需要**手写 JS 视图**
  （像 `client.js` 已经做的那样），并且要自己处理 LuCI 的 `map.reset()` 重渲染、
  轮询状态、以及"未保存即生效"带来的回滚语义。
  右侧状态栏还会**多一处状态轮询**——正好是这个会话刚合并掉的那个状态（`hp.statusPoller`），
  真做的话得复用它、并补守卫。

### 风险

- **A** 的风险是被 CBI 带偏：CBI 的默认样式偏旧，要做到稿子这个观感得覆盖相当一部分 CSS，
  而且要在 LuCI 主题升级时跟着修。
- **B** 的风险是"未保存即生效"：用户点一下单选就重载服务，误触代价是**断网几秒**。
  稿子里靠"选中即生效、不需要再找保存"来当卖点，实现上必须配**确认/撤销**，
  否则不如 A 稳妥。

## Demo C：把 路由 / DNS / 规则 归为「流量策略」

C 不是第三套视觉，而是 **A 的改版扩充**：沿用 A 的侧栏、顶栏、卡片语言，只动信息架构，
并做**一处真正的合并**。

### 为什么要归类

路由、DNS、规则回答的是同一个问题——**这段流量该怎么走**。现在它们散在四个页面里
（`client` 的 `routing` / `dns` / `ruleset` / `control`），改一条分流要来回切页，
而且新增规则时得先决定"这算路由还是 DNS"。

### 归类结果

```
流量策略
├── 策略总览     决策链：流量 → 规则匹配 → 出站 / 解析
├── 规则         ★ 路由规则 + DNS 规则 = 一张表
├── DNS          服务器 · 解析策略 · 缓存
└── 路由         模式 · 默认出站 · 路由节点 · 规则集
    （另有「访问控制」：接口 / LAN / WAN / 域名清单）
```

### 合并的底气：代码里它们已经是同一个构建器

这不是设计上的一厢情愿。`client.js` 里路由规则和 DNS 规则**本来就走同一个函数**：

```js
renderRuleSection(s, kind, self, data)      // client.js:84
  → uci_type = is_dns ? 'dns_rule' : 'routing_rule'
```

调用点只有两个：`'routing'`（1181）与 `'dns'`（1365）。两者的字段（域名 / IP / 端口 /
进程 / 规则集 + 动作）完全同构，差异只在**动作的取值范围**（路由 = 出站，DNS = DNS 服务器）
和少数 DNS 专属项。所以合成一张表之后，规则表可以直接复用这个已合并、已有测试覆盖的函数，
不需要新的状态管理——这是 C 相对 A/B 最实际的优势。

### 与现有界面的对应关系

C 的稿子里带一页「从现有界面迁移」，逐项列出旧位置 → 新位置。**没有任何功能被丢掉**：

| 现有位置 | 改版后 | 变化 |
|---|---|---|
| Client → Routing Settings / Routing Nodes | 流量策略 → 路由 | 归类 |
| Client → Routing Rules | **流量策略 → 规则（同表）** | **合并** |
| Client → DNS Settings / DNS Servers | 流量策略 → DNS | 归类 |
| Client → DNS Rules | **流量策略 → 规则（同表）** | **合并** |
| Client → Rule Set | 流量策略 → 路由 → 规则集 | 归类 |
| Client → Access Control | 流量策略 → 访问控制 | 归类，子项全留 |
| Client → DNS Cache (1.14) | 流量策略 → DNS → 解析与缓存 | 归类 |
| Node / Server / Service Status | 节点 / 服务端（入站+证书）/ 运行状态 | 基本不变 |
| — | 总览、策略总览（决策链） | **新增** |

### 落地成本

**中偏低。** 各子页仍可沿用现有的 `form.GridSection` / `NamedSection`；唯一的合并点
复用已重构好的 `renderRuleSection`。真正要新写的只有：总览卡片、策略总览的决策链区块、
规则页的类型筛选 chips（纯 CSS + 前端过滤，不碰后端）。

## Demo D：保留现有两级 tab，只调层级

现有界面是**两级 tab**：一级是 4 个 sibling 菜单项（客户端设置 / 节点设置 / 服务器设置 /
服务状态，各对应一个 view 文件），二级是 `client.js` 里那个 `NamedSection` 上的 7 个
`s.tab()`。D 不换导航范式，只做四件事：

| # | 改动 | 前 | 后 |
|---|---|---|---|
| ① | **访问控制升到一级** | 客户端设置的二级 tab | 第一层 tab（新增一个 view + 一个菜单项） |
| ② | **新增「节点配置」二级 tab** | 代理模式 / 主节点 / 主 UDP 节点散在「路由设置」里 | **节点配置**：代理模式 · 主节点 · 主 UDP 节点 · URLTest 参数 |
| ③ | **客户端设置二级收敛** | 路由设置 / 路由节点 / DNS 设置 / DNS 服务器 / 规则集 / 访问控制 / DNS 缓存（7 项） | **节点配置 / 分流设置 / DNS 设置 / 规则集设置 / 资源管理**（5 项） |
| ④ | **资源管理跨一级搬迁** | 服务状态 → 资源管理 | **客户端设置 → 资源管理** |

改版后的一级 tab 变成 **5 项**：客户端设置 · 节点设置 · 服务器设置 · **访问控制** · 服务状态。

### 为什么这四条

- **访问控制该独立**：它回答「**谁**走代理、哪些域名/IP 例外」，和「**怎么**走」
  （分流 / DNS / 规则集）不是同一层。放二级等于把"给谁用"塞进"怎么用"里。
- **「用哪个节点」该单独一页**：代理模式 + 主节点 + 主 UDP 节点回答的是
  「默认用哪个节点、以什么模式用」，而分流规则回答「哪些流量**不**走默认节点」。
  两者混在一个 tab 里，改分流时得先绕过节点选择区。
- **二级 7 项太碎**：去掉节点选择后的「路由设置」与「路由节点」都是纯分流，
  DNS 设置 + DNS 服务器 + DNS 缓存都是"解析"，各自合并成一个 tab。
- **资源管理放错了页**：它产出 geosite / geoip / 域名清单 / IP 清单，是分流与 DNS 规则的
  **原料**，跟服务运行状态没关系。放在「服务状态」等于把配置项藏在诊断页。

### 「节点配置」里必须带上 URLTest 参数

现有代码里 `main_urltest_nodes` / `main_urltest_interval` / `main_urltest_tolerance`
都写着 `depends('main_node', 'urltest')`（`client.js:697-714`），是主节点的从属项。
如果主节点搬去「节点配置」而参数留在「分流设置」，用户会看到一个
**跟节点选择脱节、而且经常是空的分流页**。所以这三项跟着主节点走。

另外 `routing_mode` 有一个 `onchange` 在选 `custom` 时**立即 `map.save()`**
（`client.js:817-827`）——这是现有行为，改版时只换 tab 名、不要动它，
但要补一句提示，免得用户以为"还没保存"。

### 规则仍然合并在一处看

D 保留各页自己的规则列表（日常改动不用来回切页），同时在
**规则集设置 → 统一规则视图**提供一张跨「分流规则 / DNS 规则」的总表，带类型筛选。
依据和 C 相同：两类规则字段同构，代码里本来就是同一个构建器
（`renderRuleSection(s, kind)`，`client.js:84`）。

### 落地要动的地方

| 动作 | 文件 |
|---|---|
| 新增一级 tab | `root/usr/share/luci/menu.d/luci-app-homeproxy.json`（`order` 排在 server=20 与 status=30 之间） |
| 新增 view | `htdocs/luci-static/resources/view/homeproxy/acl.js`（把 `s.tab('control')` 起的 5 个子 tab 整体搬过去） |
| 新增二级 tab + 收敛 | `htdocs/luci-static/resources/view/homeproxy/client.js` |
| taboption 改归属 | `client.js:688-745、817`：`main_node` / `main_urltest_*` / `main_udp_node` / `routing_mode` 的第一个参数由 `'routing'` 改成 `'nodeconf'`（**只改 tab 名，不动 `depends` 与 `onchange`**） |
| 资源管理搬家 | `status.js:218` 的 `NamedSection _('Resources management')` → `client.js` |
| ACL 权限 | `root/usr/share/rpcd/acl.d/luci-app-homeproxy.json`（漏了不报错，菜单项**直接不出现**） |

**成本：中。** 大部分是搬代码 + 改 tab 名，不新增状态管理；主要风险是权限文件和 i18n
（二级 tab 改名后 `po/` 与 `.lmo` 都要重新生成）。

## 我的建议

**选 D。** 它保留现有两级 tab 模式（不换导航范式），只调层级，最贴近"在现有 UI 上
改版扩充"：一级加一个「访问控制」，客户端设置的二级从 7 项收敛到 3 项，资源管理从
服务状态搬回客户端。改动以**搬代码 + 改 tab 名**为主，不引入新的状态管理。

**C 是 D 的"视觉升级版"**：同一套信息架构，但把导航从两级 tab 换成侧栏 + 卡片。
如果以后想要更现代的观感，可以在 D 的结构上再套 C 的样式；反过来先做 C 再退回 D 也不亏，
因为两者的分组是同一套。

**要"给不熟的人用"——取 B 的向导思路，但只取一部分**：
把三步流程用在**首次配置**，日常页面仍用 D/C 的分区式。纯 B 的"每件事都是流程"在
日常高频改动时会变累。

四稿都不排他：D 的卡片区可以直接放 B 的步骤条（"未完成配置"提示），
B 的工具轨也可以换成 D/C 的完整导航。

---

## 说明

这四个是**设计稿**，不是可用的 LuCI 页面：没有接 RPC，数据是写死的，交互只有切页/切状态/筛选。
确认方向后，实际落地还需要：接入 `rpcCall`、接上 `form.*` 或手写视图、
补测试（快照 + 不变量）、以及在真机上做一次浏览器人工回归——最后这项只能由你来。
