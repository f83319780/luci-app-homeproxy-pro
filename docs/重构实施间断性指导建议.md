# HomeProxy Pro 架构重构计划：28 项核心观点

> 本文整理此前架构审查与重构讨论中的 28 项核心观点，作为后续 Agent 执行、PR 拆分、架构验收和长期维护的基准文档。
>
> 当前判断：项目整体架构成熟度约 **80–85%**。当前重点已经不应是继续拆 Generator，而应转向**架构边界收敛、领域模型完整化、运行时可靠性和前端模块化**。

---

## 一、总体架构判断

### 01. 当前架构已经完成从“脚本堆叠”向“分层架构”的关键转型

目标架构：

```text
UCI
 ↓
Config Loader / Repository
 ↓
HomeProxy Domain Config / Node / DNS / Route / Server
 ↓
Parser / Generator / Runtime
```

订阅链路：

```text
Fetch
 ↓
Decode
 ↓
Parse
 ↓
Normalize
 ↓
Validate
 ↓
Filter
 ↓
Repository
 ↓
Domain Node
```

核心原则是：**UCI 是输入来源，Domain Model 是内部事实来源，sing-box JSON 是输出格式。**

---

### 02. 当前最大的风险已经不是 Generator 拆分不足，而是边界没有完全收敛

Generator 已经完成较大规模模块化，目前继续拆分的收益明显下降。

后续优先级应转向：

1. Domain Model 完整化
2. Parser Normalize
3. Subscription Repository / Transaction Boundary
4. Server Inbound Domain Model / Adapter
5. Runtime Reliability
6. LuCI 模块化
7. Architecture Guard + CI

因此应当**冻结 Generator 的大规模结构调整**，只接受必要的 bug fix 和小范围演进。

---

### 03. Domain Model 应成为整个系统唯一的内部事实模型

当前 `Config` / `Node` 已经建立，但 DNS、Route、Server、Inbound 等部分仍存在 raw UCI 数据结构。

最终目标：

```text
UCI
 ↓
Loader
 ↓
Domain Model
 ↓
所有业务逻辑
```

业务层、Parser、Generator、Runtime 不应再次回头读取 UCI。

---

### 04. Domain Model 不应知道 sing-box JSON

Domain Model 的职责是表达 HomeProxy 的语义，例如：

- Node
- Credentials
- TLS
- Transport
- Multiplex
- DNS
- Routing
- Server
- Inbound

它不应该出现：

```text
sing-box outbound
sing-box inbound
sing-box route.rules
sing-box transport JSON
```

等输出格式概念。

否则 Domain Model 会反向依赖 Generator，形成架构污染。

---

### 05. `raw` 字段只能作为兼容层，不能继续成为业务层逃生通道

目前部分模型仍保留 `raw`。

允许：

```text
UCI / legacy → raw
```

但不允许业务代码长期：

```text
node.raw.xxx
config.raw.xxx
```

作为正常数据访问方式。

后续应逐步把真正需要的字段提升为显式 Domain Model 字段。

---

## 二、Parser / Protocol Architecture

### 06. Parser 必须彻底变成“输入格式 → Normalized Node”的纯转换器

目标：

```text
Share Link / Subscription Text
        ↓
Parser
        ↓
Normalized Node
```

Parser 不应该：

- 写 UCI
- commit UCI
- 修改全局配置
- 直接生成 sing-box JSON
- 负责节点持久化

Parser 的输出必须稳定、可测试、可复用。

---

### 07. Parser 应统一输出 Canonical Node，而不是每种协议返回不同结构

所有协议：

```text
VLESS
VMess
Trojan
Hysteria2
TUIC
SS
SOCKS
HTTP
SSH
...
```

最终都应归一为统一 Node：

```text
Node {
  type
  address
  port
  credentials
  tls
  transport
  multiplex
  protocol_options
}
```

协议特殊字段进入：

```text
protocol_options
```

而不是创建大量协议专属顶层结构。

---

### 08. Parse、Normalize、Validate 应明确分层

推荐：

```text
Parse
 ↓
Normalize
 ↓
Validate
```

含义：

- Parse：理解输入语法
- Normalize：转换为 Canonical Node
- Validate：检查语义完整性

这样错误可以准确定位：

```text
invalid URI
invalid encoding
unsupported protocol
missing credential
invalid port
invalid TLS configuration
```

而不是最后统一变成“节点生成失败”。

---

### 09. Protocol Adapter 应负责协议差异，而不是承担配置读取职责

推荐：

```text
Domain Node
 ↓
Protocol Adapter
 ↓
sing-box Outbound
```

Adapter 应是纯函数式转换：

```text
create(node, context)
```

禁止：

```text
cursor()
uci.get()
uci.foreach()
uci.commit()
```

Adapter 不应该知道 UCI。

---

### 10. Generator 应保持“Domain → sing-box JSON”的单向职责

目标：

```text
Domain Model
 ↓
Generator
 ↓
sing-box JSON
```

Generator 不应该再：

```text
cursor()
uci.get()
uci.foreach()
```

当前这一点已经基本实现，应通过 Architecture Guard 长期保护。

---

### 11. Generator 当前拆分已经足够，后续应进入冻结状态

目前已经拆成：

```text
generator/
├── common.uc
├── client.uc
├── dns.uc
├── inbound.uc
├── outbound.uc
├── route.uc
├── ruleset.uc
└── server.uc
```

并有：

```text
generate_client.uc
generate_server.uc
```

作为薄 CLI wrapper。

这是合理结构。

后续不应为了“文件更小”继续机械拆分。

---

### 12. WireGuard 等特殊协议应通过明确的 Domain / Adapter 表达，而不是 Generator 特判

任何特殊协议都应该进入：

```text
Node
 ↓
Protocol Adapter
 ↓
Outbound
```

而不是：

```text
if wireguard ...
if special ...
if legacy ...
```

散落在 Generator 各处。

---

## 三、Subscription Architecture

### 13. Subscription 必须形成完整的纯流水线

目标：

```text
Fetch
 ↓
Decode
 ↓
Parse
 ↓
Normalize
 ↓
Validate
 ↓
Filter
 ↓
Repository
```

其中：

- Fetch：网络获取
- Decode：Base64 / 文本解码
- Parse：URI / subscription parser
- Normalize：Canonical Node
- Validate：语义校验
- Filter：去重 / 过滤 / 策略
- Repository：持久化

---

### 14. Pure Stage 不得修改 UCI

以下模块原则上应保持无副作用：

```text
decoder
parser
normalizer
validator
filter
```

禁止：

```text
uci.set()
uci.delete()
uci.commit()
```

这样每一层才能独立测试。

---

### 15. `update_subscriptions.uc` 应逐渐退化为 Orchestrator

当前它仍然承担部分：

- UCI cursor
- set
- commit
- URL 更新
- 主节点处理
- 节点 reconciliation

最终应收敛为：

```text
update_subscriptions
        ↓
fetch
        ↓
decode
        ↓
parse
        ↓
normalize
        ↓
validate
        ↓
filter
        ↓
repository
```

它本身只负责 orchestration，不负责具体业务细节。

---

### 16. Subscription Repository 应成为唯一持久化边界

Repository 负责：

```text
find
create
update
delete
replace
reconcile
```

业务层不应该散落：

```text
uci.set()
uci.delete()
uci.commit()
```

最终做到：

```text
Subscription Pipeline
 ↓
Repository
 ↓
UCI
```

---

### 17. 需要明确 Candidate / Transaction / Rollback 三层概念

推荐：

```text
Candidate Config
      ↓
Validation
      ↓
Generate
      ↓
sing-box check
      ↓
Health Check
      ↓
Commit / Activate
```

失败：

```text
Candidate failed
 ↓
Keep Known-Good
 ↓
Rollback
```

注意：不能假设不同 ucode 进程之间能够看到其他进程尚未 commit 的 UCI 修改。

因此如果要实现真正 Candidate Config，应使用：

- 独立 staging 文件
- 临时 UCI namespace
- 独立配置副本
- 或单进程内完成完整事务

不能依赖“跨进程未提交 UCI 自动可见”。

---

## 四、Runtime Reliability

### 18. Runtime 的目标不应只是“进程活着”

当前 health 主要依赖：

- `pgrep`
- ubus
- service instance

这只能证明：

```text
process alive
```

最终应验证：

```text
process alive
+
config valid
+
required listener exists
+
listener reachable
+
service responds correctly
```

也就是：

```text
Process Health
 ↓
Configuration Health
 ↓
Listener Health
 ↓
Functional Health
```

---

### 19. `init.d/homeproxy` 需要继续减负

当前 `init.d/homeproxy` 仍然很大，承担：

- lifecycle
- version gate
- dnsmasq
- firewall
- procd
- known-good
- health
- rollback

虽然已经抽出：

```text
runtime/config.sh
runtime/health.sh
```

但还没有完全收敛。

目标：

```text
init.d
 ↓
Runtime Service
 ↓
config / health / rollback helpers
```

init.d 最终只负责生命周期编排。

---

### 20. 已有 `procd respawn`，不应重复实现 daemon supervision

当前已经存在：

```text
procd_set_param respawn
```

因此不需要再在 shell 层重复实现：

```text
while true
restart loop
sleep
```

Runtime 重构应该利用 OpenWrt/procd 的 supervision 能力，而不是与之竞争。

---

### 21. Known-Good 必须成为正式 Runtime 状态

推荐状态机：

```text
KNOWN_GOOD
    ↓
CANDIDATE
    ↓
VALIDATING
    ↓
ACTIVATING
    ↓
HEALTHY
```

失败：

```text
CANDIDATE
 ↓
FAILED
 ↓
ROLLBACK
 ↓
KNOWN_GOOD
```

这样 Runtime 行为才能从“脚本顺序”变成明确状态机。

---

## 五、LuCI Frontend

### 22. 前端当前最大问题是模块重复，而不是功能不足

目前主要文件规模较大：

```text
client.js
node.js
server.js
status.js
homeproxy.js
```

整体约 4k+ 行。

重点问题：

- 协议列表重复
- TLS 配置重复
- Transport 配置重复
- 字段 metadata 重复
- Node / Server 之间存在相似 UI 构造逻辑

---

### 23. 前端协议定义应逐渐与 Backend Domain Model 对齐

不要维护：

```text
node.js protocol list
server.js protocol list
adapter.uc protocol list
model.uc protocol list
```

多个独立真相源。

理想方向：

```text
Protocol Definition
        ↓
Backend capability
        ↓
Frontend metadata
```

可以通过：

- 静态共享 metadata
- build-time generated metadata
- 明确的 capability manifest

实现。

---

### 24. 不要为了“安全感”做没有证据支持的大规模 frontend rewrite

例如仅凭代码风格就全面替换：

```text
innerHTML
DOM construction
```

如果没有实际 XSS 输入路径或可信性问题，收益不足以覆盖回归风险。

Frontend 重构应该以：

- duplication
- maintainability
- capability metadata
- component reuse

为主要目标。

---

## 六、Testing / CI / Architecture Governance

### 25. 当前测试体系已经比较强，应从“功能测试”升级到“架构不变量测试”

现有测试已经覆盖：

- generator golden
- protocol inventory
- domain model fixture
- parser
- subscription
- migration
- firewall
- runtime transaction
- LuCI snapshots
- i18n
- grammar/toolchain

下一步重点不是无限增加普通 case，而是增加 Architecture Invariant：

```text
Generator cannot use UCI
Adapter cannot use UCI
Parser cannot use UCI
Domain Model cannot depend on sing-box JSON
Pure subscription stages cannot commit
```

可以直接通过 grep/static checks 或轻量 AST 检查实现。

---

### 26. Golden / Snapshot Test 应继续作为重构安全网

已有：

```text
client.json
node.json
server.json
```

以及 generator golden / protocol golden。

这些测试对于“大规模重构但保持输出兼容”非常重要。

原则：

```text
Refactor implementation
≠
Unintended output change
```

如果行为确实需要改变，应明确更新 golden，并记录原因，而不是让 snapshot 变化被默默接受。

---

### 27. Full On-Target Test 是当前 CI 的重要剩余缺口

本地已经可以运行：

- Node
- LuCI snapshot
- i18n
- runtime transaction

但完整 ucode + sing-box 测试依赖：

```text
ucode
sing-box
```

当前本地环境未安装二者，因此 full suite 无法在本机完成。

现有 `tests/run.sh` 会在本地工具不存在时尝试通过 SSH：

```text
root@192.168.1.1
```

最终 CI 应增加稳定的：

- OpenWrt target
- QEMU
- 或持久化测试设备

确保完整测试不依赖开发者手工设备。

---

### 28. 最终必须建立 Architecture Guard，防止重构成果倒退

这是整个重构计划最重要的长期保护措施之一。

建议 CI 每次 PR 执行：

```text
check-domain-boundary
check-parser-boundary
check-adapter-boundary
check-generator-boundary
check-subscription-boundary
check-runtime-boundary
```

例如：

```text
generator/**        禁止 UCI API
adapter.uc          禁止 UCI API
parser/**           禁止 UCI API
model.uc            禁止 sing-box JSON key
subscription/pure/** 禁止 commit
```

架构规则一旦进入 CI，就不再依赖开发者“记得遵守”。

# 七、推荐的最终 PR 路线

结合上述 28 项观点，后续建议采用 7 个 PR：

## PR-01 — Domain Model Completion

目标：

- 完成 DNS / Route / Server / Inbound Domain Model
- 减少 raw UCI section
- 明确 Node / Config invariants
- 清理 legacy/raw escape hatch

---

## PR-02 — Parser Normalization

目标：

```text
Parse
 ↓
Normalize
 ↓
Validate
```

统一所有协议到 Canonical Node。

---

## PR-03 — Subscription Transaction Boundary

目标：

- 完成 Repository
- `update_subscriptions.uc` 变成 orchestrator
- pure pipeline 与 persistence 分离
- 建立 reconciliation 语义

---

## PR-04 — Protocol Adapter Completion

目标：

- 完善所有 protocol adapter
- Server inbound adapter
- WireGuard 等特殊协议统一走 adapter

---

目标：

- Candidate
- Known-Good
- Activation
- Functional Health
- Rollback

---

## PR-06 — LuCI Modularization

目标：

- shared protocol metadata
- shared TLS / Transport components

- 降低 frontend duplication

---

## PR-07 — Architecture Guard + CI

目标：

- architecture invariant tests
- dependency boundary checks
- on-target full suite
- CI regression protection

# 九、当前阶段结论

**结论：Approve with follow-up。**

项目已经完成了相当大比例的架构现代化工作：

- Domain Model 已建立
- Config Loader 已建立
- Generator 已模块化
- Adapter 已基本建立
- Subscription 已开始分层
- Runtime 已开始抽取
- Tests / Golden / Snapshot 已较完整
- i18n 已达到 100% coverage

当前最值得投入的工作，不是继续扩大重构范围，而是：

> **把已经存在的层次真正变成不可越界的架构边界。**

换句话说：

```text
Phase 1：拆开
Phase 2：归位
Phase 3：锁死边界
```

当前项目已经接近从 Phase 1 进入 Phase 2/3 的阶段。

后续每个 PR 都应回答三个问题：

1. **它属于哪一层？**
2. **它依赖哪些层？**
3. **它是否可能绕过既有边界？**

如果第三个问题答案为“是”，则应优先修改架构边界，而不是继续堆功能。
